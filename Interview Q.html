🔷 LangChain — Fundamentals
Q1 What is LangChain and what problems does it solve? LangChain

LangChain is an open-source framework (Python & JS) for building LLM-powered applications. It provides abstractions for:

  • Model I/O — unified interface to any LLM/Chat model
  • Chains — composable sequences of calls
  • Memory — conversation state management
  • Agents — LLM-directed tool use
  • Retrieval — RAG pipelines over external data

It solves boilerplate around prompt templating, output parsing, context window management, and multi-step reasoning without writing glue code from scratch.

Q2 Explain the LangChain component hierarchy. LangChain
  • Schema — base types: BaseMessage, Document, ChatGeneration
  • Models — LLM, ChatModel, Embeddings
  • Prompts — PromptTemplate, ChatPromptTemplate, FewShotPromptTemplate
  • Output Parsers — StrOutputParser, PydanticOutputParser, JsonOutputParser
  • Chains / LCEL — composable runnables
  • Memory — ConversationBufferMemory, etc.
  • Agents & Tools — ReAct, function-calling agents
  • Retrievers & Vector Stores — FAISS, Chroma, Pinecone…
  • Callbacks — tracing, logging, streaming
Q3 What is the Runnable interface and why is it central to LangChain? LangChain

Every component in LCEL implements Runnable, which exposes:

  • invoke(input) — single synchronous call
  • stream(input) — token-by-token generator
  • batch(inputs) — parallel execution
  • ainvoke / astream / abatch — async variants

Because every piece shares the same interface, you can pipe them with | regardless of whether the piece is a prompt, model, retriever, or custom function. This enables uniform composition without wrapper boilerplate.

Q4 Difference between LLM and ChatModel in LangChain? LangChain
  • LLM — takes a plain string, returns a plain string. Models: OpenAI (text-davinci-003), Cohere, etc.
  • ChatModel — takes a list of BaseMessage (SystemMessage, HumanMessage, AIMessage), returns a BaseMessage. Models: ChatOpenAI, ChatAnthropic.

Modern GPT-4, Claude, Gemini are all chat models. Prefer ChatModel for dialogue applications.

Q5 What are the main prompt template types and when to use each? LangChain
  • PromptTemplate — plain string with {variable} placeholders. Use for LLMs.
  • ChatPromptTemplate — list of message templates (system, human, ai). Use for chat models.
  • FewShotPromptTemplate — includes example selector + prefix/suffix. Good for few-shot in-context learning.
  • FewShotChatMessagePromptTemplate — few-shot for chat models.
  • MessagesPlaceholder — slot for injecting a list of messages (e.g., conversation history) into a ChatPromptTemplate.
Q6 How does LangChain handle output parsing and what parsers exist? LangChain

Output parsers transform raw model output into structured data:

  • StrOutputParser — extracts .content as plain string
  • JsonOutputParser — parses JSON from model output
  • PydanticOutputParser — validates against a Pydantic model; injects format instructions into the prompt via get_format_instructions()
  • CommaSeparatedListOutputParser
  • StructuredOutputParser — schema-driven without Pydantic
  • XMLOutputParser, MarkdownListOutputParser
💡 With model.with_structured_output(MyPydanticModel) you can skip the parser — the model itself returns validated objects via function-calling.
⛓️ Chains & LCEL
Q7 What is LCEL (LangChain Expression Language)? LangChain

LCEL is a declarative syntax introduced in LangChain v0.1 for composing Runnable components using the | pipe operator:

chain = prompt | llm | StrOutputParser()
result = chain.invoke({"topic": "black holes"})

Benefits:

  • Automatic async, streaming, and batch support
  • Built-in RunnablePassthrough, RunnableParallel, RunnableLambda
  • First-class LangSmith tracing
  • No hidden state — chains are pure data-flow graphs
Q8 Explain RunnableParallel, RunnablePassthrough, and RunnableLambda. LangChain
  • RunnableParallel — runs multiple runnables on the same input simultaneously and returns a dict of results. Great for fan-out (e.g., retrieve context AND reformat query in parallel).
  • RunnablePassthrough — passes input through unchanged. Used to thread the original question alongside retrieved docs into a prompt.
  • RunnableLambda — wraps any Python function as a Runnable so it participates in streaming and tracing.
from langchain_core.runnables import RunnableParallel, RunnablePassthrough

chain = RunnableParallel(
    context=retriever,
    question=RunnablePassthrough()
) | prompt | llm | StrOutputParser()
Q9 How does streaming work in LCEL and why does it matter? LangChain

Every Runnable exposes .stream() / .astream() returning a generator of partial outputs. LCEL propagates streaming end-to-end:

for chunk in chain.stream({"question": "Explain LCEL"}):
    print(chunk, end="", flush=True)

Matters because:

  • Reduces perceived latency in chat UIs (first token arrives quickly)
  • Lets you abort expensive calls early
  • Required for production-grade APIs and WebSocket delivery

astream_events gives fine-grained event hooks (on_llm_start, on_chain_end, etc.) useful for debugging.

Q10 What are legacy chains vs LCEL chains? When would you still use legacy? LangChain

Legacy chains (LLMChain, ConversationalRetrievalChain, RetrievalQA) predate LCEL and use class-based composition. They are now deprecated but still widely found in existing codebases.

LCEL chains are composable runnables — more transparent, better streaming, easier to test.

You might keep legacy chains when maintaining old code or using community integrations not yet rewritten.

⚠️ New projects should always use LCEL. Legacy chains will be removed in LangChain v1.x.
Q11 How do you add retry and fallback logic to a chain? LangChain 
# Retry on RateLimitError up to 3 times
robust_llm = llm.with_retry(stop_after_attempt=3)

# Fallback to a cheaper model
fallback_chain = primary_chain.with_fallbacks([backup_chain])

with_fallbacks catches exceptions from the primary and runs the fallback list in order. You can specify exceptions_to_handle to be selective.

🧠 Memory
Q12 How does conversational memory work in LangChain? LangChain

Memory objects store and retrieve conversation history. Types:

  • ConversationBufferMemory — stores all messages verbatim. Simple but grows unbounded.
  • ConversationBufferWindowMemory — keeps last k exchanges.
  • ConversationSummaryMemory — uses an LLM to summarise old messages, keeping the window small.
  • ConversationSummaryBufferMemory — hybrid: recent messages verbatim, older ones summarised.
  • ConversationTokenBufferMemory — caps by token count, not message count.
  • VectorStoreRetrieverMemory — stores messages in a vector store; retrieves semantically relevant history.
💡 In LCEL-first apps, manage history explicitly with RunnableWithMessageHistory + a BaseChatMessageHistory backend (Redis, DynamoDB, etc.).
Q13 What is RunnableWithMessageHistory and how does it work? LangChain

It wraps any LCEL chain to automatically inject and persist conversation history per session_id:

from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_community.chat_message_histories import RedisChatMessageHistory

chain_with_history = RunnableWithMessageHistory(
    chain,
    get_session_history=lambda sid: RedisChatMessageHistory(sid, url=REDIS_URL),
    input_messages_key="question",
    history_messages_key="history",
)
chain_with_history.invoke(
    {"question": "Who won the World Cup in 2022?"},
    config={"configurable": {"session_id": "user-42"}}
)

It reads history before the call and writes back after, transparently.

Q14 How do you avoid context-window overflow in long conversations? LangChain
  • Windowing — keep only last N messages (ConversationBufferWindowMemory)
  • Summarisation — periodically summarise old turns
  • Token trimming — trim_messages() utility trims to a max token budget
  • Semantic compression — store turns in a vector DB; retrieve only relevant ones
  • Structured memory — extract key facts into a structured store (entity memory)
🤖 Agents & Tools
Q15 What is a LangChain agent and how does it work? LangChain

An agent uses an LLM as a reasoning engine to decide which tool(s) to call and in what order, based on the user goal. The flow:

  1. LLM receives the prompt + available tool descriptions
  2. LLM outputs an action (tool name + input) or a final answer
  3. The agent executor invokes the tool and feeds the result back
  4. Loop until the LLM decides to stop

Core agent types: ReAct (Reason + Act), OpenAI Functions/Tools, Structured Chat, XML.

Q16 How do you create a custom tool in LangChain? LangChain 
from langchain_core.tools import tool

@tool
def get_stock_price(ticker: str) -> str:
    """Return the latest stock price for the given ticker symbol."""
    # ... call your API
    return f"{ticker}: $123.45"

The docstring becomes the tool description the LLM uses. For complex input schemas, annotate with Pydantic:

from pydantic import BaseModel, Field

class StockInput(BaseModel):
    ticker: str = Field(description="Ticker symbol, e.g. AAPL")

@tool(args_schema=StockInput)
def get_stock_price(ticker: str) -> str:
    """Return the latest stock price."""
    ...
Q17 Explain the ReAct agent pattern. LangChain

ReAct (Reasoning + Acting) prompts the LLM to interleave thought and action steps:

Thought: I need to find the population of France.
Action: wikipedia_search
Action Input: {"query": "France population 2024"}
Observation: France has ~68 million people.
Thought: I have the answer.
Final Answer: France's population is approximately 68 million.

Advantages: transparent reasoning, works with any LLM. Disadvantages: verbose, slower, susceptible to hallucinated tool calls.

Q18 What is the difference between AgentExecutor and a LangGraph agent? LangChainLangGraph
  • AgentExecutor — a simple while-loop runner for legacy agents. Good for linear tool-use flows. Hard to customise mid-loop.
  • LangGraph agent — the agent loop is an explicit state machine graph. You control every node, edge, and conditional branch. Supports cycles, human-in-the-loop, parallel tool calls, multi-agent topologies.

New production agents should use LangGraph. AgentExecutor is maintained for backward compatibility.

Q19 How does tool calling (function calling) differ from ReAct? LangChain
  • ReAct — text-based; LLM writes "Action: tool_name" in free text. Prompt-heavy, no structured guarantee.
  • Tool/Function calling — model natively outputs structured JSON tool calls (e.g., OpenAI's tool_calls field). More reliable, supports parallel tool calls, no prompt engineering for output format.

In LangChain: llm.bind_tools(tools) enables function-calling; create_tool_calling_agent builds the full agent.

Q20 How do you handle tool errors gracefully in an agent? LangChain
  • Use handle_tool_error=True on AgentExecutor — feeds the exception message back to the LLM as an observation so it can retry or recover.
  • Set handle_tool_error to a callable for custom error messages.
  • Mark tools as return_direct=True to skip LLM post-processing for terminal tools.
  • In LangGraph, add an explicit error-handling node or use try/except inside a node function.
📚 RAG (Retrieval-Augmented Generation)
Q21 Explain the RAG pipeline step by step. LangChain
  1. Load — ingest documents with loaders (PyPDFLoader, WebBaseLoader, UnstructuredLoader, etc.)
  2. Split — chunk documents with RecursiveCharacterTextSplitter or semantic splitters
  3. Embed — convert chunks to vectors using an embedding model
  4. Store — persist vectors in a vector store (Chroma, FAISS, Pinecone, Weaviate)
  5. Retrieve — at query time, embed the question and do similarity search
  6. Generate — pass retrieved chunks + question to LLM to produce grounded answer
Q22 What retrieval strategies exist beyond naive similarity search? LangChain
  • MMR (Maximal Marginal Relevance) — balances relevance and diversity in results
  • Self-query retriever — LLM converts natural language query into vector store filter expressions
  • Multi-query retriever — generates multiple phrasings of the query, merges results
  • Contextual compression — extracts only relevant sentences from retrieved chunks
  • Parent-document retriever — stores small chunks for retrieval but returns the larger parent document for context
  • Ensemble retriever — fuses dense (vector) + sparse (BM25) results via RRF
  • HyDE (Hypothetical Document Embeddings) — generate a hypothetical answer, embed it, then retrieve
Q23 What is the difference between sparse and dense retrieval? LangChain
  • Sparse (BM25/TF-IDF) — keyword-based, exact term matching. Fast, no embedding needed. Good for factual queries with unique terms.
  • Dense (vector search) — semantic similarity via embeddings. Handles paraphrasing and synonyms. Slower index build but excellent recall.
  • Hybrid — combines both scores (often with Reciprocal Rank Fusion). Best of both worlds. Supported by Pinecone, Weaviate, Azure AI Search.
Q24 How do you evaluate RAG quality? LangChain

Key metrics:

  • Faithfulness — is the answer grounded in retrieved context? (no hallucination)
  • Answer relevancy — does the answer address the question?
  • Context precision / recall — are the right chunks retrieved?

Tooling: RAGAS, LangSmith evaluators, TruLens. Can use LLM-as-judge with a rubric.

Q25 Explain chunk size strategy and its impact on RAG performance. LangChain
  • Too small chunks — high precision in retrieval, but each chunk may lack sufficient context for the LLM to answer well.
  • Too large chunks — more context per chunk, but vector representation diluted; recall suffers; chunks may exceed context window.
  • Typical sweet spot: 256–1024 tokens with 10–20% overlap.
  • Semantic chunking — splits at natural topic boundaries rather than fixed size.
  • Parent-child strategy — small chunks for retrieval, large parents for generation context.

Q26 What is the LangChain callback system? LangChain

Callbacks are event hooks fired at lifecycle points. Implement BaseCallbackHandler:

Pass via config={"callbacks": [MyHandler()]} or globally via environment. Used for logging, streaming to UI, cost tracking, and observability.

Features:

  • Prompt playground
🔶 LangGraph — Core Concepts
Q28 What is LangGraph and how does it differ from LCEL chains? LangGraph

LangGraph is a library for building stateful, cyclic LLM workflows modelled as directed graphs (nodes + edges). Key differences from LCEL:

  • Cycles — LangGraph supports loops; LCEL is a DAG.
  • Explicit state — a typed TypedDict state is passed and mutated across nodes.
  • Conditional branching — edges can be functions deciding the next node.
  • Persistence — built-in checkpointing between steps.
  • Human-in-the-loop — interrupt at any node, resume after human approval.

LCEL = pipeline. LangGraph = state machine / workflow engine.

Q29 Explain the three core building blocks of a LangGraph application. LangGraph
  1. State — a TypedDict (or Pydantic model) defining all data flowing through the graph. Each node receives the full state and returns a partial update.
  2. Nodes — Python functions (or runnables) that accept the state dict and return a dict of updates. Represent discrete computation steps.
  3. Edges — connections between nodes. Can be:
    • Normal edges: always go from A to B
    • Conditional edges: call a routing function to decide the next node dynamically
    • Entry/exit points: START and END special nodes
Q30 What is the StateGraph and how do you compile it? LangGraph 
from langgraph.graph import StateGraph, END
from typing import TypedDict

class AgentState(TypedDict):
    messages: list
    tool_results: list

graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.set_entry_point("agent")
graph.add_conditional_edges("agent", should_continue, {
    "continue": "tools",
    "end": END
})
graph.add_edge("tools", "agent")

app = graph.compile()
result = app.invoke({"messages": [HumanMessage(content="Hello")]})

compile() validates the graph structure and returns a CompiledGraph which is itself a Runnable (supports invoke, stream, batch).

Q31 How does state update work — what are reducers? LangGraph

By default, node return values overwrite the corresponding state keys. To append instead, annotate the field with a reducer using Annotated:

from typing import Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]  # appends, not overwrites

add_messages is a built-in reducer that appends new messages and deduplicates by ID. You can write custom reducers for any merge logic.

Q32 Explain START and END nodes in LangGraph. LangGraph

START is a virtual entry node — you connect it to the first real node via set_entry_point or add_edge(START, "node_name"). It injects the initial input into the graph state.

END is a virtual terminal node. When any edge routes to END, the graph halts and returns the current state. You can have multiple paths to END.

Q33 What are conditional edges and how do you implement routing? LangGraph 
def route_agent(state: AgentState) -> str:
    last_message = state["messages"][-1]
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "tools"
    return "end"

graph.add_conditional_edges(
    "agent",
    route_agent,
    {"tools": "tools", "end": END}
)

The routing function receives the current state and returns a string key, which is looked up in the mapping dict to find the next node. You can also return a Send object for dynamic fan-out.

💾 LangGraph — State & Persistence
Q34 What is checkpointing in LangGraph and why does it matter? LangGraph

A checkpointer persists the graph state after every node execution. This enables:

  • Human-in-the-loop — pause execution, wait for approval, resume
  • Fault tolerance — resume after crash/timeout
  • Time travel — replay from any historical checkpoint
  • Multi-turn conversations — maintain per-session state across HTTP requests
from langgraph.checkpoint.sqlite import SqliteSaver

with SqliteSaver.from_conn_string(":memory:") as memory:
    app = graph.compile(checkpointer=memory)
    config = {"configurable": {"thread_id": "session-1"}}
    app.invoke({"messages": [...]}, config=config)
Q35 What checkpointer backends does LangGraph support? LangGraph
  • MemorySaver — in-process dict. Development/testing only.
  • SqliteSaver — SQLite file. Single-process prod use.
  • AsyncSqliteSaver — async SQLite.
  • PostgresSaver / AsyncPostgresSaver — production-grade, multi-process safe.
  • RedisSaver — community integration.
  • Custom: implement BaseCheckpointSaver.
Q36 How does thread-based state work in LangGraph? LangGraph

Every invocation is associated with a thread_id in the config. All checkpoints for the same thread form a conversation history. Different thread IDs maintain completely isolated state — essential for multi-user applications.

# User A
app.invoke(input, config={"configurable": {"thread_id": "user-a"}})

# User B — isolated state
app.invoke(input, config={"configurable": {"thread_id": "user-b"}})

You can also use checkpoint_id to target a specific historical snapshot (time travel).

Q37 Explain human-in-the-loop interrupts in LangGraph. LangGraph

Compile with interrupt_before or interrupt_after to pause execution at specific nodes:

app = graph.compile(
    checkpointer=memory,
    interrupt_before=["tools"]  # pause before calling tools
)

# First call — runs until interrupt
app.invoke(input, config=config)

# Human reviews, then resumes
app.invoke(None, config=config)  # None = use checkpointed state

The interrupt() function (LangGraph 0.2+) can also be called inside a node for dynamic interrupts with a value passed to the caller.

Q38 What is time travel in LangGraph? LangGraph

Because every node execution is checkpointed, you can:

  • Replay — re-execute from any past checkpoint with get_state_history(config) to list snapshots
  • Branch — fork from a historical state to explore alternate paths
  • Update — use update_state(config, values, as_node=...) to inject corrected data and then resume

Useful for debugging agents that went wrong mid-run.

🚀 LangGraph — Advanced Patterns
Q39 What is the Send API and when do you use it? LangGraph

Send enables dynamic fan-out — spawning multiple parallel graph executions with different states from a single node. Use it for map-reduce patterns:

from langgraph.types import Send

def generate_tasks(state):
    return [Send("process_item", {"item": item}) for item in state["items"]]

graph.add_conditional_edges("planner", generate_tasks)

Each Send creates an independent sub-invocation of the target node. Results are aggregated via reducers on the parent state.

Q40 Explain subgraphs in LangGraph. LangGraph

A compiled graph is itself a Runnable and can be embedded as a node inside a parent graph. This enables:

  • Modularity — encapsulate complex logic (e.g., a RAG subgraph, a reflection loop)
  • Reuse — share the same subgraph across multiple parent graphs
  • Independent state — subgraph has its own StateSchema; the parent maps keys via input_map / output_map
rag_graph = build_rag_graph().compile()
parent_graph.add_node("rag", rag_graph)
Q41 How do you build a multi-agent system in LangGraph? LangGraph

Common topologies:

  • Supervisor — a "manager" node calls worker agents (subgraphs) based on a task routing decision. Worker results feed back to the supervisor.
  • Network / Swarm — agents can hand off to any other agent dynamically; state carries the conversation and a routing history.
  • Hierarchical — supervisor of supervisors; subgraphs within subgraphs.
# Supervisor pattern
def supervisor_node(state):
    decision = llm.invoke(supervisor_prompt.format_messages(**state))
    return {"next": decision.tool_calls[0].args["worker"]}

LangGraph's langgraph-supervisor package provides a pre-built supervisor factory.

Q42 What is the prebuilt create_react_agent in LangGraph? LangGraph 
from langgraph.prebuilt import create_react_agent

agent = create_react_agent(
    model=ChatOpenAI(model="gpt-4o"),
    tools=[search, calculator],
    state_modifier="You are a helpful assistant."
)
result = agent.invoke({"messages": [HumanMessage(content="What is 42 * 1337?")]})

It's a pre-built LangGraph that implements the standard tool-calling agent loop (agent → tools → agent → … → end). Fully customisable — you can add nodes/edges on top of it.

Q43 How does streaming work differently in LangGraph vs LCEL? LangGraph

LangGraph's stream() emits graph-level events in addition to token-level chunks:

for event in app.stream(input, config=config, stream_mode="values"):
    print(event)  # full state after each node

for event in app.stream(input, config=config, stream_mode="updates"):
    print(event)  # only the delta from each node

# LLM token streaming inside nodes:
async for event in app.astream_events(input, config=config, version="v2"):
    if event["event"] == "on_chat_model_stream":
        print(event["data"]["chunk"].content, end="")

Stream modes: "values", "updates", "debug", "messages" (token-level).

Q44 What are Command objects in LangGraph? LangGraph

Nodes can return a Command instead of a plain dict. Command combines state update + routing decision in one return value:

from langgraph.types import Command

def my_node(state):
    return Command(
        update={"result": "done"},
        goto="next_node"         # or END
    )

This is especially useful when the routing logic is inside the node rather than in a separate router function — keeps all branching logic co-located with the computation.

Q45 Explain LangGraph's persistence store vs checkpointer. LangGraph
  • Checkpointer — stores graph run state keyed by (thread_id, checkpoint_id). Scoped to a single run/conversation. Auto-managed.
  • Store (BaseStore) — a key-value store for long-term memory shared across threads. Manually read/write from nodes. Use for user profile, learned facts, cross-session memory.
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
app = graph.compile(checkpointer=memory, store=store)

# Inside a node:
def agent_node(state, store):
    profile = store.get(("users",), user_id)
    store.put(("users",), user_id, {"preference": "concise"})
Q46 How do you implement a reflection / self-critique loop in LangGraph? LangGraph

Add a "critique" node after the "generate" node. A conditional edge checks the critique score:

graph.add_node("generate", generate_node)
graph.add_node("critique", critique_node)
graph.add_edge("generate", "critique")
graph.add_conditional_edges("critique", check_quality, {
    "pass": END,
    "revise": "generate"  # loop back
})

Add a revision_count field to state and cap it to prevent infinite loops.

Q47 What is Plan-and-Execute in LangGraph? LangGraph

A two-phase agent pattern:

  1. Planner node — LLM decomposes the goal into a list of sub-tasks
  2. Executor loop — iterates through sub-tasks, calling tools for each
  3. Replanner node — (optional) after each task, re-evaluate the plan based on results

Benefits over pure ReAct: better for long-horizon tasks; plan is inspectable; can parallelise independent tasks with Send.

LangGraph Platform is a managed infrastructure layer for deploying LangGraph applications:

  • LangGraph Server — REST API + WebSocket server auto-generated from your graph
  • Persistence — managed Postgres checkpointing

# langgraph.json

  "dependencies": ["."],

Q49 How do you serve a LangChain/LangGraph app in production? LangChainLangGraph
  • LangServe — FastAPI wrapper that exposes LCEL chains as /invoke, /stream, /batch endpoints with auto-generated OpenAPI docs and a playground UI at /playground.
  • LangGraph Server — purpose-built for LangGraph; adds assistants API, thread management, streaming SSE.
  • Custom FastAPI/Flask — call app.invoke() / app.astream() directly inside your endpoints.
💡 For new projects, prefer LangGraph Server over LangServe.
Q50 How do you manage costs and rate limits when calling LLMs in production? LangChain
  • Caching — set_llm_cache(SQLiteCache()) or Redis/Semantic cache; identical prompts return cached responses.
  • Semantic cache (RedisSemanticCache) — cache based on embedding similarity, not exact match.
  • Retry with backoff — llm.with_retry() handles transient 429s.
  • Callbacks for cost tracking — OpenAICallbackHandler tracks tokens + cost per run.
  • Model selection — route simple tasks to cheaper models, complex to expensive ones.
  • Prompt compression — trim context, use retrieval to avoid stuffing full documents.
Q51 How do you test LangChain / LangGraph applications? Both
  • Unit test nodes — each LangGraph node is just a Python function; test with mock state dicts.
  • Mock LLMs — use FakeListChatModel or FakeChatModel from langchain_core.language_models.fake for deterministic tests.
  • Trace-based evaluation — collect LangSmith traces from staging, create a dataset, run evals.
  • Integration tests — run full graph with a test checkpointer (MemorySaver).
  • RAGAS / TruLens — automated RAG quality metrics.
Q52 How do you handle secrets and configuration in LangChain? LangChain
  • Pass API keys via environment variables, never hardcode.
  • Use SecretStr from Pydantic — prevents accidental logging of sensitive values.
  • Use RunnableConfig to pass runtime configuration (model params, tenant IDs) without baking into the chain definition.
  • Store secrets in a vault (Azure Key Vault, AWS Secrets Manager) and inject at startup.

Q54 How does LangChain compare to alternatives like LlamaIndex, Haystack, or raw OpenAI SDK? LangChain
  • LlamaIndex — data-centric; excels at complex retrieval pipelines, query engines over structured/unstructured data. Less focus on agents/workflows.
  • Haystack — pipeline-based, strong in NLP/search pipelines, good enterprise tooling, stronger typing in newer v2.
  • Raw OpenAI SDK — zero abstraction overhead; best when you only use one model and want full control. No portability.
  • LangChain — broadest ecosystem; best for multi-model, multi-tool applications; LCEL gives flexibility; LangGraph for complex agent workflows.
Q55 What are common pitfalls with LangChain in production? LangChain
  • Context window creep — unbounded memory causing 4k→8k→16k token explosions
  • Verbose dependency tree — langchain is a heavy package; use langchain-core + specific integrations
  • Using deprecated chains — LLMChain, ConversationalRetrievalChain should be replaced with LCEL
  • No observability — running blind without LangSmith or another tracer
  • Prompt injection — user input incorporated into system prompts without sanitisation
  • Tight coupling to one LLM provider — breaking when the API changes
Q56 What are common LangGraph anti-patterns? LangGraph
  • No max-iteration guard — agent loops forever; always add a step_count field and a conditional edge that routes to END after N steps
  • Mutating state in-place — nodes must return dicts, not modify the state object directly
  • Using MemorySaver in prod — process restarts lose all state
  • Ignoring thread_id — all users share the same state
  • Over-complex single graphs — decompose into subgraphs for maintainability
  • No interrupt/approval for dangerous tools — calling irreversible APIs (send email, delete DB) without human confirmation
Q57 How do you implement structured output with LangChain and why is it important? LangChain

Structured output ensures LLM responses conform to a schema — critical for downstream code that parses results:

from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

class MovieReview(BaseModel):
    title: str = Field(description="Movie title")
    rating: int = Field(description="Rating out of 10")
    summary: str = Field(description="Brief summary")

llm = ChatOpenAI(model="gpt-4o")
structured_llm = llm.with_structured_output(MovieReview)
review = structured_llm.invoke("Review Inception")

Uses function-calling under the hood — far more reliable than parsing free-text JSON.

Q58 Explain the LangChain package split (langchain-core, langchain, langchain-community). LangChain
  • langchain-core — base abstractions (Runnable, BaseMessage, BaseChatModel, etc.). Minimal dependencies. Every other package depends on this.
  • langchain — higher-level chains, agents, memory classes. Depends on core.
  • langchain-community — third-party integrations (vector stores, loaders, tools). Loosely coupled, maintained by community.
  • langchain-openai, langchain-anthropic, etc. — official first-party provider packages. Prefer over community equivalents.
  • langgraph — separate package for the graph runtime.
Q59 How do you implement semantic caching for LLM calls? LangChain 
from langchain_community.cache import RedisSemanticCache
from langchain_openai import OpenAIEmbeddings
import langchain

langchain.llm_cache = RedisSemanticCache(
    redis_url="redis://localhost:6379",
    embedding=OpenAIEmbeddings(),
    score_threshold=0.2   # cosine distance threshold
)

When a new prompt's embedding is within score_threshold of a cached prompt, the cached response is returned without calling the LLM. Dramatically reduces costs for similar repeated queries.

Q60 Walk through building a production-ready RAG agent with LangGraph end to end. Both
  1. Index pipeline (offline): Load → Split → Embed → Store in Chroma/Pinecone
  2. Define state: {"messages": Annotated[list, add_messages], "context": list}
  3. Router node: LLM decides — RAG or direct answer
  4. Retrieve node: call retriever, store docs in state["context"]
  5. Generate node: build prompt with context + messages → call LLM → append AIMessage
  6. Grade node: (optional) LLM checks faithfulness → loop if hallucination detected
  7. Compile with PostgresSaver for persistence
  8. Serve via LangGraph Server or FastAPI with astream_events for SSE streaming
  9. Observe with LangSmith; evaluate with RAGAS on sampled traces
💡 This is the CRAG (Corrective RAG) pattern — adding a hallucination check loop significantly improves production reliability.
