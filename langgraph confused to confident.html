How State Flows Through Nodes

This is the single most confusing thing for beginners. Let's kill the confusion permanently.

What is State, really?

State is just a Python dictionary that LangGraph manages for you. It holds all the information your graph needs — messages, counters, user names, whatever you define. Every node reads from this dict and writes back to it.

┌──────────────────────────────────────────────────────────┐ │ THE LANGGRAPH LOOP │ │ │ │ State (dict) ──────→ Node Function ──────→ State │ │ { "count": 0 } reads state (merged) │ │ { "name": "Alice" } returns partial dict update │ │ │ │ RULE: node receives FULL state, returns PARTIAL update │ └──────────────────────────────────────────────────────────┘

Step 1 — Define your State with TypedDict

TypedDict is just a typed dictionary. It tells Python (and your IDE) what keys exist and their types. LangGraph uses this as the schema for every node.

state_basics.py 
from typing import TypedDict, Annotated
from langgraph.graph.message import add_messages

# ─── Define your state schema ────────────────────────────────────────────────
class MyState(TypedDict):
    # TypedDict = a Python dict with named fields and type hints.
    # These are the ONLY fields LangGraph tracks.

    messages: Annotated[list, add_messages]
    # ↑ SPECIAL FIELD: add_messages is a "reducer".
    # Normal dict update = REPLACE the whole list.
    # add_messages reducer = APPEND new messages to existing list.
    # Without this, every node call would WIPE your chat history!

    user_name: str          # a simple string field — just replaced on update
    turn_count: int         # a counter — just replaced on update

# ─── What this looks like as an actual runtime value ─────────────────────────
example_state = {
    "messages": [],         # starts empty
    "user_name": "Alice",
    "turn_count": 0,
}
# LangGraph holds this dict and passes it to each node automatically.
⚠️ The #1 Beginner Mistake — Forgetting add_messages

If you write messages: list instead of messages: Annotated[list, add_messages], every time a node runs it will replace (not append) the messages list. Your conversation history will disappear after every step. Always use Annotated[list, add_messages] for chat messages.

Step 2 — Write a Node Function

A node is just a regular Python function. LangGraph automatically passes the current state to it. The node must return a dict of only the fields it wants to update.

node_basics.py 
from langchain_core.messages import HumanMessage, AIMessage

# ─── A node is JUST a Python function ────────────────────────────────────────
#     Signature: def my_node(state: MyState) -> dict
#     LangGraph calls this automatically with the current state.

def chatbot_node(state: MyState) -> dict:
    # ─── READ from state like a normal dict ──────────────────────────────────
    all_messages = state["messages"]   # the full list of messages so far
    user_name    = state["user_name"]  # the user's name
    turn_count   = state["turn_count"] # how many turns have happened

    print(f"Turn {turn_count}: Processing {len(all_messages)} messages")

    # ─── Do your LLM call ────────────────────────────────────────────────────
    system_msg = SystemMessage(content=f"You are a helpful assistant. The user's name is {user_name}.")
    response   = llm.invoke([system_msg] + all_messages)
    # response is an AIMessage object from the LLM

    # ─── RETURN only the fields you want to UPDATE ───────────────────────────
    # You do NOT need to return the full state.
    # LangGraph merges what you return with the existing state.
    return {
        "messages":   [response],          # add_messages will APPEND this AIMessage
        "turn_count": turn_count + 1,      # increment the counter (replaces old value)
        # "user_name" is NOT returned — LangGraph keeps it unchanged automatically
    }

# ─── KEY INSIGHT ─────────────────────────────────────────────────────────────
# "messages" gets APPENDED  (because of add_messages reducer)
# "turn_count" gets REPLACED (no reducer = simple replace)
# "user_name" stays the SAME  (not returned = untouched)

Step 3 — Build the Graph

graph_basics.py 
from langgraph.graph import StateGraph, START, END

# ─── 1. Create a builder with your state schema ──────────────────────────────
builder = StateGraph(MyState)

# ─── 2. Add nodes ────────────────────────────────────────────────────────────
#    add_node("name_you_choose", the_python_function)
builder.add_node("chatbot", chatbot_node)

# ─── 3. Add edges ────────────────────────────────────────────────────────────
#    START is a special built-in node that represents the entry point.
#    END   is a special built-in node that terminates the graph.
builder.add_edge(START, "chatbot")   # graph starts → chatbot node
builder.add_edge("chatbot", END)     # chatbot node → graph ends

# ─── 4. Compile ──────────────────────────────────────────────────────────────
#    compile() locks the graph and makes it runnable.
graph = builder.compile()

# ─── 5. Run ──────────────────────────────────────────────────────────────────
initial_state = {
    "messages":   [HumanMessage(content="Hello!")],
    "user_name":  "Alice",
    "turn_count": 0,
}
result = graph.invoke(initial_state)
print(result["messages"][-1].content)  # the AI's reply

Visual: How LangGraph passes state

BEFORE invoke(): state = { "messages": [HumanMessage("Hi")], "turn_count": 0 } │ ▼ ┌─────────────────────────────────────────┐ │ chatbot_node(state) is called │ │ state["messages"] → [HumanMessage] │ │ state["turn_count"] → 0 │ │ │ │ returns: { "messages": [AIMessage], │ │ "turn_count": 1 } │ └─────────────────────────────────────────┘ │ ▼ AFTER invoke(): state = { "messages": [HumanMessage("Hi"), AIMessage("Hello!")], "turn_count": 1, "user_name": "Alice" } ↑ add_messages APPENDED ↑ unchanged
💡 The Trick to Write Nodes Without Thinking

Always use this 3-part template when writing any node:

1. READ — value = state["key"]
2. COMPUTE — do your logic, call LLM, transform data
3. RETURN — return {"key": new_value} (only changed fields)

That's it. Every single node in LangGraph follows this exact pattern.

ReAct Pattern — What, Why, and How

ReAct stands for Reasoning + Acting. It is the most common agent pattern in the world. Understanding it will let you build almost any real AI agent.

The Problem it Solves

A plain LLM can only generate text. It can't look things up, run calculations, check databases, or call APIs. What if we want an AI that can actually do things in the world?

The solution: Give the LLM access to tools, and let it decide which tool to call, run it, see the result, and keep going until the task is done.

ReAct Loop: User Question │ ▼ ┌─────────────────────────────────────────────────────────┐ │ AGENT NODE (LLM thinks) │ │ "I need to search for the capital of France" │ │ → Decides to call tool: search("capital of France") │ └──────────────────┬──────────────────────────────────────┘ │ tool_call in response ▼ ┌─────────────────────────────────────────────────────────┐ │ TOOLS NODE (executes the function) │ │ search("capital of France") → "Paris" │ └──────────────────┬──────────────────────────────────────┘ │ ToolMessage with result ▼ ┌─────────────────────────────────────────────────────────┐ │ AGENT NODE again (LLM sees the result) │ │ "The answer is Paris. I'm done." │ │ → No more tool calls → route to END │ └──────────────────┬──────────────────────────────────────┘ │ ▼ Final Answer

Why a Loop?

This is why LangGraph exists. Simple tools like LangChain's AgentExecutor were hard to customize and control. LangGraph models the reasoning loop as a graph — you can see every step, add custom logic, pause mid-loop, inject human feedback, and more.

Implementation: The Easy Way (Prebuilt)

LangGraph ships a prebuilt ReAct agent. Use this to get started fast.

react_prebuilt.py 
from langchain_core.tools import tool
from langgraph.prebuilt import create_react_agent

# ─── Step 1: Define tools ─────────────────────────────────────────────────────
# A tool is just a Python function decorated with @tool.
# The docstring is CRITICAL — the LLM reads it to understand what the tool does!

@tool
def get_weather(city: str) -> str:
    """Get the current weather for a city. Use this when asked about weather."""
    # In a real app, you'd call a weather API here.
    weather_data = {
        "New York": "72°F, Sunny",
        "London": "58°F, Cloudy",
        "Tokyo": "68°F, Partly Cloudy",
    }
    return weather_data.get(city, f"Weather data not available for {city}")

@tool
def calculate(expression: str) -> str:
    """Safely evaluate a math expression. Input must be a valid Python math expression."""
    try:
        # SECURITY NOTE: use ast.literal_eval or numexpr in production!
        # For demo purposes only:
        allowed = set("0123456789+-*/(). ")
        if all(c in allowed for c in expression):
            return str(eval(expression))  # noqa: S307
        return "Invalid expression"
    except Exception as e:
        return f"Error: {e}"

# ─── Step 2: Bundle tools into a list ─────────────────────────────────────────
tools = [get_weather, calculate]

# ─── Step 3: Create the ReAct agent in ONE line ───────────────────────────────
agent = create_react_agent(
    model=llm,      # your AzureChatOpenAI instance
    tools=tools,    # list of tools the agent can use
)

# ─── Step 4: Run it ───────────────────────────────────────────────────────────
result = agent.invoke({
    "messages": [HumanMessage(content="What's the weather in London and what is 15 * 23?")]
})

# The agent will: call get_weather("London"), then call calculate("15 * 23"), then answer.
for msg in result["messages"]:
    print(f"{msg.__class__.__name__}: {msg.content[:100]}")

Implementation: The Manual Way (Full Control)

Build it yourself when you need custom logic — custom prompts, special routing, interrupts, etc.

react_manual.py 
from typing import Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode     # handles tool execution automatically
from langchain_core.messages import SystemMessage

# ─── State ────────────────────────────────────────────────────────────────────
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]

# ─── Bind tools to the LLM ────────────────────────────────────────────────────
# This is the magic step. When the LLM is "bound" to tools, it knows they exist
# and can choose to call them by including a tool_calls block in its response.
llm_with_tools = llm.bind_tools(tools)

# ─── Node 1: The "brain" — LLM decides what to do next ───────────────────────
def agent_node(state: AgentState) -> dict:
    system = SystemMessage(content="You are a helpful assistant. Use tools when needed.")
    response = llm_with_tools.invoke([system] + state["messages"])
    # response will either be:
    # - a normal AIMessage (LLM is done, no tools needed)
    # - an AIMessage with .tool_calls (LLM wants to call a tool)
    return {"messages": [response]}

# ─── Node 2: The "hands" — executes the tool calls ───────────────────────────
# ToolNode is prebuilt. It looks at the last AIMessage, finds .tool_calls,
# runs each tool function, and returns ToolMessage results.
tool_node = ToolNode(tools)   # pass the same tools list

# ─── Conditional Router — "should we call tools or are we done?" ──────────────
def should_continue(state: AgentState) -> str:
    last_message = state["messages"][-1]   # what did the LLM just say?

    if last_message.tool_calls:
        # LLM included tool_calls → go run the tools
        return "tools"
    else:
        # No tool calls → LLM is done → end the graph
        return END

# ─── Build the graph ──────────────────────────────────────────────────────────
builder = StateGraph(AgentState)
builder.add_node("agent", agent_node)
builder.add_node("tools", tool_node)

builder.add_edge(START, "agent")    # always start with the agent

# Conditional edge: after "agent" runs, call should_continue() to decide next step
builder.add_conditional_edges(
    "agent",             # from this node
    should_continue,     # call this function to get the next node name
    ["tools", END],      # possible destinations (optional, for documentation)
)

builder.add_edge("tools", "agent")  # after tools run → back to agent for next thought

graph = builder.compile()

# ─── Test ─────────────────────────────────────────────────────────────────────
result = graph.invoke({"messages": [HumanMessage(content="What is 144 / 12?")]})
print(result["messages"][-1].content)
💡 Trick: How to write conditional edges every time

A conditional edge router always follows the same pattern:
def router(state) → str — inspect the state, return a string that matches a node name or END. It's just an if/else that returns strings.

Reflexion Agent

Reflexion is a pattern where an AI agent critiques its own output and then improves it. Instead of giving one answer, it goes through a loop: generate → reflect → revise → repeat.

Why Reflexion?

LLMs often give mediocre first answers. If you ask the same LLM to critique that answer and then improve it, the second (or third) answer is significantly better. Reflexion automates this process.

Reflexion Loop: ┌─────────────┐ ┌─────────────────┐ ┌──────────────────┐ │ GENERATE │────►│ REFLECT │────►│ Good enough? │ │ Write an │ │ Critique the │ │ YES → END │ │ answer │◄────│ answer. What's │ │ NO → Generate │ └─────────────┘ │ missing? Wrong? │ │ again (improved)│ └─────────────────┘ └──────────────────┘ The key: the reflection/critique is added to the messages, so the next "Generate" call sees the critique and can improve.
reflexion_agent.py 
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

# ─── State ────────────────────────────────────────────────────────────────────
class ReflexionState(TypedDict):
    task: str               # the original task/question from the user
    messages: Annotated[list, add_messages]  # full conversation including critiques
    iteration: int          # how many times we've looped
    max_iterations: int     # stop after this many loops to avoid infinite loop

# ─── Node 1: GENERATE ─────────────────────────────────────────────────────────
# First time: write an answer.
# Later times: improve based on the critique in messages.
def generate_node(state: ReflexionState) -> dict:
    # On first iteration, messages has just the task.
    # On later iterations, messages also has the previous answer + critique.
    # The LLM will see all of this and produce an improved answer.

    response = llm.invoke(state["messages"])
    print(f"\n[Generate - Iteration {state['iteration'] + 1}]")
    print(response.content[:200])  # preview

    return {
        "messages": [response],    # append the generated answer
        "iteration": state["iteration"] + 1,
    }

# ─── Node 2: REFLECT ──────────────────────────────────────────────────────────
# Critically evaluate the last generated answer.
def reflect_node(state: ReflexionState) -> dict:
    last_answer = state["messages"][-1].content  # the most recent generation

    critique_prompt = f"""You are a critical reviewer. 

Task that was given: {state['task']}

The answer provided was:
{last_answer}

Critique this answer. Be specific:
- What is missing or incomplete?
- What is factually wrong?
- What could be improved or clarified?

If the answer is genuinely excellent and complete, say "ACCEPT: " followed by your reason.
Otherwise say "REVISE: " followed by specific improvement instructions."""

    critique = llm.invoke([HumanMessage(content=critique_prompt)])
    print(f"\n[Reflect] {critique.content[:200]}")

    return {
        # We add the critique as an AIMessage so generate_node sees it next
        "messages": [AIMessage(content=f"[CRITIQUE]: {critique.content}")],
    }

# ─── Conditional Router ───────────────────────────────────────────────────────
def should_continue_reflexion(state: ReflexionState) -> str:
    # Stop if: max iterations reached OR last critique says ACCEPT
    if state["iteration"] >= state["max_iterations"]:
        print("\n[Router] Max iterations reached. Stopping.")
        return END

    last_message = state["messages"][-1].content
    if "ACCEPT:" in last_message:
        print("\n[Router] Critique accepted the answer. Stopping.")
        return END

    print(f"\n[Router] Revision needed. Loop {state['iteration']}/{state['max_iterations']}")
    return "generate"   # go back to generate with the critique in context

# ─── Build the graph ──────────────────────────────────────────────────────────
builder = StateGraph(ReflexionState)
builder.add_node("generate", generate_node)
builder.add_node("reflect",  reflect_node)

builder.add_edge(START, "generate")
builder.add_edge("generate", "reflect")

builder.add_conditional_edges(
    "reflect",                    # after reflect, decide:
    should_continue_reflexion,    # check if we should continue
    ["generate", END],            # possible next steps
)

reflexion_graph = builder.compile()

# ─── Run ──────────────────────────────────────────────────────────────────────
task = "Explain the difference between supervised and unsupervised machine learning in simple terms."

initial_state = {
    "task": task,
    "messages": [
        HumanMessage(content=f"Task: {task}\n\nPlease write a clear, complete answer.")
    ],
    "iteration": 0,
    "max_iterations": 3,   # will loop at most 3 times
}

result = reflexion_graph.invoke(initial_state)

# Get the final answer (last non-critique message)
final_messages = [m for m in result["messages"] if "[CRITIQUE]" not in m.content]
print("\n=== FINAL ANSWER ===")
print(final_messages[-1].content)
🔑 The Key Insight of Reflexion

The secret is that the critique becomes part of the message history. When generate_node runs again, the LLM sees its own previous answer and the critique in the conversation. It naturally produces a better answer. No magic — just prompting in a loop.

StateGraph vs MessageGraph

This confuses everyone. Here is the definitive answer.

The Short Answer

MessageGraph is deprecated. You should always use StateGraph today. MessagesState (note: different from MessageGraph) is the recommended starting point for chatbots.

StateGraph MessageGraph (deprecated) StateGraph + MessagesState
State shape You define it (TypedDict) Just a list of messages, hard-coded Pre-built: just messages, but extensible
Custom fields ✓ Yes ✗ No ✓ Yes (extend it)
Status ✓ Current ✗ Deprecated ✓ Recommended
Use when Complex agents with custom state Don't use Chatbots, simple agents
Node signature def n(state: YourState) def n(messages: list) def n(state: MessagesState)

MessagesState — The Convenient Shortcut

MessagesState is just a pre-defined TypedDict with one field: messages with add_messages. LangGraph ships it so you don't have to write it yourself for simple cases.

messages_state_comparison.py 
from langgraph.graph import MessagesState, StateGraph, START, END

# ─── Option A: MessagesState shortcut ────────────────────────────────────────
# Use this for simple chatbots. State has only "messages".

builder = StateGraph(MessagesState)
# nodes receive state["messages"] automatically

# ─── Option B: Custom StateGraph (most common in real apps) ──────────────────
# Use this when you need more than just messages.

class AdvancedState(TypedDict):
    messages: Annotated[list, add_messages]   # chat history
    user_id: str                               # who is talking
    session_topic: str                         # current topic
    tool_call_count: int                       # how many tools called so far
    user_preferences: dict                     # any preferences learned

builder2 = StateGraph(AdvancedState)

# ─── The equivalence: MessagesState is literally just this ────────────────────
# You can think of MessagesState as:
class MessagesStateEquivalent(TypedDict):
    messages: Annotated[list, add_messages]
# That's it. The shortcut just saves you from writing these 2 lines.

# ─── NEVER do this (MessageGraph — deprecated) ────────────────────────────────
# from langgraph.graph import MessageGraph   ← DON'T USE
# builder = MessageGraph()                   ← DON'T USE
💡 Rule of Thumb

Start with StateGraph(MessagesState). When you need to track anything beyond messages (user info, counters, flags, etc.) switch to a custom TypedDict.

Why Do We Need Memory? The Stateless Problem

This is the most important conceptual leap in LangGraph. Let's understand the problem first.

The Problem: LangGraph is Stateless by Default

Every time you call graph.invoke(), LangGraph creates a brand new state from scratch. The previous conversation is completely gone. This is fine for a one-shot task, but terrible for a chatbot.

stateless_problem.py — BROKEN example (no memory) 
from langgraph.graph import MessagesState, StateGraph, START, END

def chatbot(state):
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(MessagesState)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)
graph = builder.compile()   # ← no checkpointer = no memory!

# Turn 1
result1 = graph.invoke({"messages": [HumanMessage(content="My name is Alice")]})
print(result1["messages"][-1].content)  # "Nice to meet you, Alice!"

# Turn 2 — PROBLEM!
result2 = graph.invoke({"messages": [HumanMessage(content="What is my name?")]})
print(result2["messages"][-1].content)
# Output: "I don't know your name. Could you tell me?"  ← FORGOT Alice!

# WHY? Because invoke() started a FRESH state.
# result1 was thrown away. result2 has no idea about Alice.

The Solution: A Checkpointer

A checkpointer is an object that saves the full state after every step, keyed by a thread_id. When you invoke again with the same thread_id, LangGraph loads the saved state automatically. This is "memory."

WITHOUT checkpointer: invoke() → fresh state → run nodes → return result → state is DISCARDED WITH checkpointer + thread_id: invoke() → load saved state for thread_id ──────────────────────────────┐ → merge with new input │ → run nodes │ → save updated state for thread_id ◄────────────────────────── ┘ → return result thread_id = a unique string that identifies ONE conversation. Think of it as a conversation ID or session ID.
🧠 Two Kinds of Memory
  • Short-term memory (in-graph): The messages in the state — the current conversation history. The LLM can "remember" things because they're in the message list it reads.
  • Long-term memory (cross-graph): A separate vector store or database where you proactively store and retrieve facts across different conversations.
  • Checkpointers handle short-term memory. For long-term memory you need external stores (covered in the full LangGraph docs).

SQLite Checkpointer — Persistent Memory

LangGraph ships two built-in checkpointers. Use MemorySaver for development and testing, and SqliteSaver for a real app that survives restarts.

checkpointers.py — all options side by side 
import sqlite3
from langgraph.checkpoint.memory  import MemorySaver
from langgraph.checkpoint.sqlite  import SqliteSaver

# ─── Option 1: MemorySaver ────────────────────────────────────────────────────
# Stores state in a Python dict in RAM.
# PROS: zero setup, great for testing.
# CONS: all conversations lost when your script ends.

memory_saver = MemorySaver()

# ─── Option 2: SqliteSaver — in-memory SQLite ────────────────────────────────
# Still in RAM (":memory:"), but uses SQLite structures.
# Slightly more overhead than MemorySaver, same ephemeral limitation.

sqlite_memory = SqliteSaver.from_conn_string(":memory:")

# ─── Option 3: SqliteSaver — file-based SQLite (RECOMMENDED for apps) ────────
# Persists conversations to a file on disk.
# Conversations survive script restarts!

conn = sqlite3.connect("chatbot_memory.db", check_same_thread=False)
#                                           ↑ needed if multiple threads access it
sqlite_file = SqliteSaver(conn)

# ─── Attach checkpointer when compiling ───────────────────────────────────────
graph_with_memory = builder.compile(checkpointer=sqlite_file)
# That single keyword argument is all it takes!

Using thread_id — The Key to Multi-user Support

Every invoke() or stream() call must include a config dict with a thread_id. LangGraph uses this to save/load the right conversation.

thread_id_demo.py 
from langchain_core.messages import HumanMessage

# ─── Config is how you pass thread_id ─────────────────────────────────────────
# Format is always: {"configurable": {"thread_id": "some_string"}}
# Use any unique string — user ID, session ID, UUID, etc.

config_alice = {"configurable": {"thread_id": "alice_session_1"}}
config_bob   = {"configurable": {"thread_id": "bob_session_1"}}

# ─── Alice's conversation ─────────────────────────────────────────────────────
result = graph_with_memory.invoke(
    {"messages": [HumanMessage(content="Hi! I'm Alice. I love cats.")]},
    config_alice,   # ← always pass config with thread_id
)
print("Alice turn 1:", result["messages"][-1].content)

result = graph_with_memory.invoke(
    {"messages": [HumanMessage(content="What do I love?")]},
    config_alice,   # ← same thread_id → remembers Alice loves cats
)
print("Alice turn 2:", result["messages"][-1].content)
# Output: "You mentioned you love cats!"

# ─── Bob's conversation — completely separate ─────────────────────────────────
result = graph_with_memory.invoke(
    {"messages": [HumanMessage(content="What do I love?")]},
    config_bob,   # ← different thread_id → fresh conversation, no Alice info
)
print("Bob turn 1:", result["messages"][-1].content)
# Output: "I don't know yet — could you tell me?"

# ─── Inspect saved state ──────────────────────────────────────────────────────
saved_state = graph_with_memory.get_state(config_alice)
print("\nSaved messages for Alice:")
for msg in saved_state.values["messages"]:
    print(f"  {msg.__class__.__name__}: {msg.content[:60]}")
💡 Trick: Think of thread_id as a "conversation folder"

The SQLite database is like a filing cabinet. Each thread_id is a folder. Every conversation lives in its own folder. When you invoke with a thread_id, LangGraph opens that folder and picks up where the conversation left off.

⚠️ Always pass config — it's easy to forget!

If you forget the config argument, LangGraph uses a temporary thread. Your memory checkpointer won't save anything and you'll wonder why memory isn't working. Rule: if your graph has a checkpointer, always pass config.

Human in the Loop

Human-in-the-loop (HITL) means pausing the graph mid-execution to get a human's input or approval before continuing. This is critical for:

  • Reviewing an agent's planned action before it executes (e.g., "Are you sure you want to delete this file?")
  • Asking the user for missing information mid-flow
  • Collecting feedback to improve the agent's next step
🔑 HITL requires a checkpointer

When the graph pauses for human input, the state must be saved somewhere so it can be resumed later. You cannot do HITL without a checkpointer.

Method 1: interrupt() — Pause inside a node (recommended)

The interrupt() function, called inside a node, pauses the graph and sends a message to the human. When the human responds, the graph resumes from exactly where it left off.

hitl_interrupt.py 
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import StateGraph, START, END

class ReviewState(TypedDict):
    messages:       Annotated[list, add_messages]
    draft_answer:   str    # the AI's draft answer before human review
    approved:       bool   # did the human approve it?
    human_feedback: str    # what did the human say?

# ─── Node 1: AI generates a draft ─────────────────────────────────────────────
def generate_draft(state: ReviewState) -> dict:
    response = llm.invoke(state["messages"])
    return {
        "draft_answer": response.content,
        "messages": [response],
    }

# ─── Node 2: Human review — PAUSES HERE and waits ─────────────────────────────
def human_review(state: ReviewState) -> dict:
    print(f"\n--- DRAFT ANSWER ---\n{state['draft_answer']}\n---")

    # interrupt() PAUSES the graph and returns control to the caller.
    # The string you pass is shown to the human as a prompt.
    # The graph will NOT continue until you call invoke() with a Command.
    feedback = interrupt(
        "Please review the draft answer above. "
        "Type 'approve' to accept, or type your feedback to request changes."
    )
    # Code below interrupt() runs AFTER the human responds.
    approved = feedback.lower().strip() == "approve"
    return {
        "human_feedback": feedback,
        "approved": approved,
    }

# ─── Node 3: Revise if not approved ───────────────────────────────────────────
def revise_or_finalize(state: ReviewState) -> dict:
    if state["approved"]:
        final_msg = f"✅ Final answer (approved):\n{state['draft_answer']}"
    else:
        # Regenerate with the human's feedback
        revision_prompt = (
            f"Original answer: {state['draft_answer']}\n\n"
            f"Human feedback: {state['human_feedback']}\n\n"
            "Please revise the answer based on this feedback."
        )
        revised = llm.invoke([HumanMessage(content=revision_prompt)])
        final_msg = f"✏️ Revised answer:\n{revised.content}"
    return {"messages": [AIMessage(content=final_msg)]}

# ─── Build ────────────────────────────────────────────────────────────────────
builder = StateGraph(ReviewState)
builder.add_node("generate",  generate_draft)
builder.add_node("review",    human_review)
builder.add_node("finalize",  revise_or_finalize)

builder.add_edge(START,      "generate")
builder.add_edge("generate", "review")
builder.add_edge("review",   "finalize")
builder.add_edge("finalize", END)

memory = MemorySaver()   # MUST have a checkpointer for HITL
hitl_graph = builder.compile(checkpointer=memory)

# ─── HOW TO RUN WITH HITL ─────────────────────────────────────────────────────
config = {"configurable": {"thread_id": "review-session-1"}}

initial_state = {
    "messages":       [HumanMessage(content="Explain what a neural network is in one paragraph.")],
    "draft_answer":   "",
    "approved":       False,
    "human_feedback": "",
}

# Step 1: Run the graph — it will pause at interrupt()
print("Running graph...")
result = hitl_graph.invoke(initial_state, config)
# result is None or incomplete because the graph paused.
# Check the current state:
current_state = hitl_graph.get_state(config)
print("Graph paused. Interrupt value:", current_state.tasks[0].interrupts[0].value)

# Step 2: Human provides input. Resume with Command(resume=...).
from langgraph.types import Command

# Option A: Human approves
human_input = "approve"

# Option B: Human requests changes
# human_input = "Please make it simpler, no technical jargon."

final_result = hitl_graph.invoke(Command(resume=human_input), config)
print("\n=== FINAL ===")
print(final_result["messages"][-1].content)

Method 2: interrupt_before — Pause before a node runs

Set at compile time. Pauses the graph before a specific node runs every time. Good when you always want to review before a certain action (e.g., a "send email" node).

interrupt_before.py 
# ─── Compile with interrupt_before ───────────────────────────────────────────
graph_with_pause = builder.compile(
    checkpointer=memory,
    interrupt_before=["send_email"],  # pause BEFORE this node runs
    # interrupt_after=["tool_node"],  # or pause AFTER a node
)

config = {"configurable": {"thread_id": "email-session-1"}}

# Run — graph will stop just before "send_email" node
result = graph_with_pause.invoke(initial_state, config)

# Inspect what the agent was about to do
state = graph_with_pause.get_state(config)
print("Agent wants to send:", state.values)

# Approve and resume — this will now run the "send_email" node
graph_with_pause.invoke(None, config)   # pass None to just continue
# or update state before resuming:
# graph_with_pause.update_state(config, {"recipient": "corrected@email.com"})
# graph_with_pause.invoke(None, config)
💡 interrupt() vs interrupt_before — when to use which?

Use interrupt() inside a node when you need dynamic pausing (e.g., only pause if the confidence score is low, or to ask a specific question based on context).

Use interrupt_before at compile time when you always want to pause before a specific action regardless of context (e.g., always review before sending an email).

Multi-turn Conversations

A multi-turn conversation is a back-and-forth chat where the AI remembers everything said so far. This combines everything: State, add_messages, a checkpointer, and thread_id.

How it actually works under the hood

Turn 1 (thread: "chat-1"): ───────────────────────────────────────────────────────────────── invoke({"messages": [HumanMessage("Hi Alice!")]}, config) │ ▼ Checkpointer loads state for "chat-1" (empty, first time) ▼ Merge: state = { messages: [HumanMessage("Hi Alice!")] } ▼ chatbot_node runs → LLM sees [HumanMessage("Hi Alice!")] ▼ LLM returns AIMessage("Hello! I'm Alice...") ▼ add_messages appends → state = { messages: [Human, AI] } ▼ Checkpointer SAVES state for "chat-1" Turn 2 (thread: "chat-1"): ───────────────────────────────────────────────────────────────── invoke({"messages": [HumanMessage("What's my name?")]}, config) │ ▼ Checkpointer LOADS state for "chat-1" ▼ Merge: state.messages = [Human1, AI1] + [HumanMessage("What?")] ▼ chatbot_node runs → LLM sees ALL 3 messages ▼ LLM returns AIMessage("I called you Alice earlier!") ▼ add_messages appends → 4 messages total ▼ Checkpointer SAVES
multi_turn_chat.py — complete working example 
import sqlite3
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.sqlite import SqliteSaver
from langchain_core.messages import HumanMessage, SystemMessage

# ─── State ────────────────────────────────────────────────────────────────────
class ChatState(TypedDict):
    messages: Annotated[list, add_messages]

# ─── Node ─────────────────────────────────────────────────────────────────────
SYSTEM_PROMPT = SystemMessage(content=(
    "You are a friendly AI assistant. "
    "You have a great memory and always refer back to things the user told you."
))

def chatbot(state: ChatState) -> dict:
    # state["messages"] already contains ALL previous messages
    # (loaded by the checkpointer automatically)
    all_messages = [SYSTEM_PROMPT] + state["messages"]
    response = llm.invoke(all_messages)
    return {"messages": [response]}   # add_messages will append this

# ─── Build ────────────────────────────────────────────────────────────────────
builder = StateGraph(ChatState)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

conn   = sqlite3.connect("chat_history.db", check_same_thread=False)
memory = SqliteSaver(conn)
graph  = builder.compile(checkpointer=memory)

# ─── Interactive multi-turn loop ──────────────────────────────────────────────
def chat(user_id: str):
    """Run a multi-turn chat for a specific user."""
    config = {"configurable": {"thread_id": f"user_{user_id}"}}
    print(f"Chatting as user: {user_id}. Type 'quit' to exit, 'history' to see messages.\n")

    while True:
        user_input = input("You: ").strip()
        if not user_input:
            continue
        if user_input.lower() == "quit":
            break
        if user_input.lower() == "history":
            state = graph.get_state(config)
            for i, msg in enumerate(state.values["messages"]):
                print(f"  [{i+1}] {msg.__class__.__name__}: {msg.content[:80]}")
            continue

        # Send message — LangGraph loads history, adds this, runs, saves.
        result = graph.invoke(
            {"messages": [HumanMessage(content=user_input)]},
            config,
        )
        print(f"AI: {result['messages'][-1].content}\n")

# To run:
# chat("alice")
# chat("bob")   # completely separate conversation
✅ Multi-turn in 5 key facts
  • 1. State has messages: Annotated[list, add_messages]
  • 2. Graph compiled with checkpointer=SqliteSaver(...)
  • 3. Every invoke passes config = {"configurable": {"thread_id": "unique_id"}}
  • 4. LangGraph auto-loads old state and auto-merges new messages
  • 5. LLM sees full history because all messages are in state["messages"]

# ─── Node 1: The main chatbot brain ───────────────────────────────────────────
def chatbot_node(state: AppState) -> dict:
    system_content = (
        "You are a friendly, helpful AI assistant with a great memory. "
        "You have access to a calculator, note-saving tool, and time tool. "
    )
    if state.get("user_name"):
        system_content += f"The user's name is {state['user_name']}. "
    system_content += "Always be concise and helpful."

    response = llm_with_tools.invoke(
        [SystemMessage(content=system_content)] + state["messages"]
    )
    return {"messages": [response]}

# ─── Node 2: Tool executor ────────────────────────────────────────────────────
# ToolNode is prebuilt — it finds tool_calls in the last AIMessage,
# runs each tool function, and returns ToolMessages with the results.
tool_executor = ToolNode(tools)

# ─── Node 3: Human approval for note-saving ───────────────────────────────────
# We pause here if the agent wants to save a note.
def approval_node(state: AppState) -> dict:
    last_msg = state["messages"][-1]

    # Check if the agent is trying to call "save_note"
    needs_approval = any(
        tc["name"] == "save_note"
        for tc in (last_msg.tool_calls if hasattr(last_msg, "tool_calls") else [])
    )

    if needs_approval:
        # Find what note they want to save
        note_call = next(
            (tc for tc in last_msg.tool_calls if tc["name"] == "save_note"), None
        )
        desc = f"Save note: '{note_call['args'].get('title')}' - {note_call['args'].get('content')}"

        # PAUSE HERE — ask human for approval
        decision = interrupt(
            f"\n🔔 APPROVAL NEEDED\n{desc}\n\nType 'yes' to approve or 'no' to cancel: "
        )
        if decision.lower().strip() == "yes":
            return {"needs_approval": False, "pending_action_desc": ""}
        else:
            # Cancel the tool call by overwriting the last message
            return {
                "messages": [AIMessage(content="I've cancelled the note-saving as requested.")],
                "needs_approval": False,
            }

    return {"needs_approval": False}

# ─── Conditional Router 1: after chatbot, route to tools or end ───────────────
def route_after_chatbot(state: AppState) -> str:
    last_msg = state["messages"][-1]

    if not hasattr(last_msg, "tool_calls") or not last_msg.tool_calls:
        return END   # no tool calls → conversation is done for this turn

    # Check if any tool needs approval
    tool_names = [tc["name"] for tc in last_msg.tool_calls]
    if "save_note" in tool_names:
        return "approval"   # route to human approval first

    return "tools"   # other tools: run directly

# ─── Conditional Router 2: after approval, either run tools or end ────────────
def route_after_approval(state: AppState) -> str:
    # If the approval node cancelled the action, last message is a plain AIMessage
    last_msg = state["messages"][-1]
    if hasattr(last_msg, "tool_calls") and last_msg.tool_calls:
        return "tools"   # approved → run tools
    return END           # cancelled → end

    print("    LangGraph Chatbot — Multi-turn with Memory & HITL")
    print("=" * 60)

    user_id = input("Enter your user ID (or press Enter for 'guest'): ").strip()
    user_id = user_id or "guest"
    config  = {"configurable": {"thread_id": f"user_{user_id}"}}

    # Initial state (only used on first run for this user; ignored on resume)
    initial_state: AppState = {
        "messages":            [],
        "user_name":           "",
        "tool_use_count":      0,
        "needs_approval":      False,
        "pending_action_desc": "",
    }

    print(f"\nLoaded session for user: {user_id}")
    print("Commands: 'quit' → exit | 'history' → show messages | 'clear' → new session\n")

    while True:
        user_input = input("You: ").strip()
        if not user_input:
            continue

        if user_input.lower() == "quit":
            print("Goodbye!")
            break

        if user_input.lower() == "history":
            state = app.get_state(config)
            if state.values:
                for i, msg in enumerate(state.values.get("messages", [])):
                    prefix = "👤" if msg.__class__.__name__ == "HumanMessage" else "🤖"
                    print(f"  {prefix} {msg.content[:100]}")
            else:
                print("  (no history yet)")
            continue

        if user_input.lower() == "clear":
            # Start a new session with a different thread_id
            config = {"configurable": {"thread_id": f"user_{user_id}_new"}}
            print("Started new session.\n")
            continue

        # ─── Invoke the graph ──────────────────────────────────────────────────
        try:
            result = app.invoke(
                {"messages": [HumanMessage(content=user_input)]},
                config,

            # Check if graph paused for human approval (interrupt)
            current_state = app.get_state(config)

            # Print the final AI response
            if result and result.get("messages"):
                ai_msg = result["messages"][-1]
                if hasattr(ai_msg, "content") and ai_msg.content:
                    print(f"AI: {ai_msg.content}\n")

        except Exception as e:
            print(f"Error: {e}\n")

Trick 7 — How to think about writing a new graph

1

Sketch the flow on paper first

Draw boxes (nodes) and arrows (edges). Don't touch code. What are the steps? What decides the next step?

2

Define your State

Ask: "What information does every node need access to?" Each answer is a field in your TypedDict.

3

Write each node as a plain function

Forget LangGraph. Write the Python function that does the work. Then wrap it in the node template (read → compute → return dict).

4

Write routers as simple if/else

A router is just: look at state, return a string. The string is the next node name or END.

5

Assemble using the template

add_node → add_edge/add_conditional_edges → compile. Always in this order.

6

Test with stream_mode="updates"

Stream to see which node is running and what it outputs. This is how you debug LangGraph.

💡 The Mental Model That Makes Everything Click

LangGraph is just a while loop with a dictionary.

Every iteration of the loop: pick a node based on routing logic → call that node function with the dict → update the dict with what the function returned → check if we're done.

The "graph" is just a fancy way of defining which function runs next. Everything else is just Python.

Streaming

Streaming lets you see the graph's output token-by-token or node-by-node as it runs, instead of waiting for the entire execution to finish. This makes your app feel instant and allows real-time UIs.

Four Stream Modes — Which One Do You Need?

ModeWhat you getBest for
"values" Full state snapshot after each node completes Debugging, seeing full state evolution
"updates" Only the delta (what each node returned) Monitoring which nodes ran and what they changed
"messages" LLM tokens as they stream, plus message metadata Chat UIs — show text appearing word by word
"debug" Everything — all internal events Deep debugging only (very verbose)

stream_mode="updates" — See Every Node Step

streaming_updates.py 
from langgraph.graph import StateGraph, MessagesState, START, END
from langchain_core.messages import HumanMessage

# Build your graph (any graph)
builder = StateGraph(MessagesState)
builder.add_node("chatbot", lambda s: {"messages": [llm.invoke(s["messages"])]})
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)
graph = builder.compile()

# ─── Stream with "updates" mode ───────────────────────────────────────────────
# Each chunk is: { "node_name": { ...what that node returned... } }
for chunk in graph.stream(
    {"messages": [HumanMessage(content="Tell me a fun fact about Python.")]},
    stream_mode="updates",
):
    for node_name, node_output in chunk.items():
        print(f"\n── Node: {node_name} ──")
        if "messages" in node_output:
            last_msg = node_output["messages"][-1]
            print(f"  {last_msg.__class__.__name__}: {last_msg.content[:200]}")
        else:
            print(f"  Output: {node_output}")

stream_mode="messages" — Token-by-Token for Chat UIs

This is the mode you use in production chat applications. Each chunk contains a single token (or small group of tokens) as the LLM generates it, plus metadata about which node emitted it.

LangGraph Subgraphs

A subgraph is a compiled LangGraph graph that is used as a node inside another (parent) graph. Subgraphs let you decompose complex systems into reusable, independently-testable components — exactly like functions in regular programming.

Why Subgraphs?

  • Modularity: build and test each agent independently, then compose them.
  • Reuse: the same subgraph can be used in multiple parent graphs.
  • Isolation: subgraphs have their own state — they can't accidentally corrupt the parent's state.
  • Team scale: different teams can own different subgraphs.
Parent Graph Subgraph A Subgraph B ──────────────────── ────────────────────── ────────────────────── START START START │ │ │ ▼ ▼ ▼ router_node fetch_data_node analyze_node │ (calls subgraph_a) │ │ ▼ ▼ ▼ [SubGraph A] ────────────→ transform_node score_node │ (calls subgraph_b) │ │ ▼ ▼ ▼ [SubGraph B] END END │ ▼ final_node │ ▼ END

State Communication: Parent ↔ Subgraph

The parent graph and subgraph have separate state schemas. LangGraph automatically maps shared fields by name. Any field with the same name in both schemas is passed through automatically.

subgraph_basic.py 
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

# ══════════════════════════════════════════════════════════════════
#  SUBGRAPH: Research Agent — searches and summarises information
# ══════════════════════════════════════════════════════════════════

class ResearchState(TypedDict):
    """State used ONLY inside the research subgraph."""
    messages:    Annotated[list, add_messages]  # shared with parent (same name)
    query:       str      # search query to run
    raw_results: list     # raw search snippets
    summary:     str      # final summarised answer

def search_node(state: ResearchState) -> dict:
    """Simulate a web search."""
    query = state["query"]
    # In a real app: call Bing/Google/Azure AI Search here
    fake_results = [
        f"Result 1 about '{query}': LangGraph is a stateful graph framework...",
        f"Result 2 about '{query}': It supports multi-agent architectures...",
        f"Result 3 about '{query}': Built on top of LangChain...",
    ]
    return {"raw_results": fake_results}

def summarise_node(state: ResearchState) -> dict:
    """Summarise the raw search results into a clean answer."""
    context = "\n".join(state["raw_results"])
    prompt  = f"Summarise these search results for the query '{state['query']}':\n\n{context}"
    summary = llm.invoke([HumanMessage(content=prompt)])
    return {
        "summary":  summary.content,
        "messages": [AIMessage(content=f"Research summary: {summary.content}")],
    }

research_builder = StateGraph(ResearchState)
research_builder.add_node("search",    search_node)
research_builder.add_node("summarise", summarise_node)
research_builder.add_edge(START,      "search")
research_builder.add_edge("search",   "summarise")
research_builder.add_edge("summarise", END)

#  PARENT GRAPH: Orchestrates research + final answer
# ══════════════════════════════════════════════════════════════════

class ParentState(TypedDict):
    """Parent graph state. 'messages' is shared with the subgraph (same field name)."""
    messages: Annotated[list, add_messages]
    query:    str       # also shared — parent sets it, subgraph reads it
    summary:  str       # also shared — subgraph sets it, parent reads it

    """Extract the search query from the user's last message."""
    user_msg = state["messages"][-1].content
    # In production: use LLM to extract the query.
    # For demo: just use the message as the query directly.

def final_answer_node(state: ParentState) -> dict:

        f"Based on this research summary:\n{state['summary']}\n\n"
        "Write a clear, helpful answer for the user."
    )

                         HumanMessage(content=prompt)])

parent_builder.add_node("extract_query", extract_query_node)

# ─── Wrap the subgraph in a regular node for custom state mapping ─────────────
def call_research_subgraph(state: ParentState) -> dict:
    """Manually translate parent state → subgraph input → parent update."""
    # Map parent fields to subgraph fields
    subgraph_input = {
        "messages":    state["messages"],
        "query":       state["user_query"],      # parent uses "user_query"
        "raw_results": [],
        "summary":     "",
    }

    # Run the subgraph
    subgraph_result = research_subgraph.invoke(subgraph_input)

    # Map subgraph results back to parent fields
    return {
        "messages":      subgraph_result["messages"],
        "research_done": True,                           # parent field
        "last_summary":  subgraph_result["summary"],     # parent uses "last_summary"
    }

# Add this wrapper as a node in the parent graph instead of the raw subgraph
parent_builder.add_node("research", call_research_subgraph)

Multi-Agent Pattern with Subgraphs

Multi-Agent Architecture: Parent Supervisor Graph ┌─────────────────────────────────────────────────────────────┐ │ START → supervisor_node │ │ │ │ │ ┌────────┼────────┐ │ │ ▼ ▼ ▼ │ │ [Researcher] [Coder] [Writer] ← each is a subgraph │ │ └────────┴────────┘ │ │ │ │ │ aggregator_node → END │ └─────────────────────────────────────────────────────────────┘ supervisor_node decides which subgraph(s) to invoke based on the user's request.
🔑 Subgraph Rules
  • A subgraph is just compiled_graph passed to add_node() — no special syntax needed.
  • Fields with the same name in both state schemas are automatically shared.
  • Each subgraph can have its own checkpointer (or inherit the parent's).
  • Subgraphs can be nested — a subgraph can itself contain another subgraph.
  • Test subgraphs independently before wiring them into the parent.

from typing import TypedDict, Annotated, List
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_core.documents import Document
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

# ─── State ────────────────────────────────────────────────────────────────────
class RAGState(TypedDict):

Pattern 2 — Corrective RAG (CRAG)

Corrective RAG adds a relevance grader after retrieval. If the retrieved documents are not relevant enough, the graph re-routes to a different retrieval strategy (e.g., broader search or web search) before generating. This prevents hallucination from poor retrieval.

Corrective RAG Flow: question │ ▼ [retrieve] → Azure AI Search (hybrid) │ ▼ [grade_docs] ← LLM rates each doc: "relevant" / "not relevant" │ ├── all relevant? ──────────────────────────────► [generate] → answer │ └── some not relevant? │ ▼ [rewrite_query] ← LLM rewrites the question for better retrieval │ ▼ [retrieve again] → broader search │ ▼ [generate] → answer
corrective_rag.py 
from typing import TypedDict, Annotated, List, Literal
from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, START, END
from langchain_core.documents import Document
from langchain_core.messages import HumanMessage, SystemMessage, AIMessage

# ─── Grading schema (structured output) ──────────────────────────────────────
class DocumentGrade(BaseModel):
    """Binary relevance grade for a retrieved document."""
    score: Literal["yes", "no"] = Field(
        description="'yes' if the document is relevant to the question, 'no' otherwise."
    )

grader_llm = llm.with_structured_output(DocumentGrade)

# ─── State ────────────────────────────────────────────────────────────────────
class CRAGState(TypedDict):
    messages:         Annotated[list, add_messages]
    question:         str
    retrieved_docs:   List[Document]
    filtered_docs:    List[Document]   # only relevant docs
    context:          str
    answer:           str
    retry_count:      int

# ─── Node 1: Retrieve ─────────────────────────────────────────────────────────
def retrieve_node(state: CRAGState) -> dict:
    docs = vector_store.similarity_search(state["question"], k=5, search_type="hybrid")
    return {"retrieved_docs": docs}

# ─── Node 2: Grade each document ─────────────────────────────────────────────
def grade_documents_node(state: CRAGState) -> dict:
    question = state["question"]
    filtered = []
    for doc in state["retrieved_docs"]:
        grade_prompt = (
            f"Question: {question}\n\n"
            f"Document:\n{doc.page_content}\n\n"
            "Is this document relevant to answering the question?"
        )
        result = grader_llm.invoke([HumanMessage(content=grade_prompt)])
        if result.score == "yes":
            filtered.append(doc)

    print(f"[Grade] {len(filtered)}/{len(state['retrieved_docs'])} docs are relevant.")
    context = "\n\n---\n\n".join([d.page_content for d in filtered])
    return {"filtered_docs": filtered, "context": context}

# ─── Node 3: Rewrite query if needed ─────────────────────────────────────────
def rewrite_query_node(state: CRAGState) -> dict:
    rewrite_prompt = (
        f"The original question '{state['question']}' returned poor search results. "
        "Rewrite it to be more specific and search-friendly. Return only the rewritten question."
    )
    new_query = llm.invoke([HumanMessage(content=rewrite_prompt)])
    print(f"[Rewrite] New query: {new_query.content}")
    return {"question": new_query.content, "retry_count": state["retry_count"] + 1}

# ─── Node 4: Generate ─────────────────────────────────────────────────────────
def generate_node(state: CRAGState) -> dict:
    if not state["context"]:
        answer = "I could not find relevant information to answer your question."
    else:
        prompt = (
            f"Answer the question using ONLY this context:\n\n"
            f"{state['context']}\n\nQuestion: {state['question']}"
        )
        resp   = llm.invoke([SystemMessage(content="Answer strictly from context."),
                              HumanMessage(content=prompt)])
        answer = resp.content

    return {"answer": answer, "messages": [AIMessage(content=answer)]}

# ─── Router: after grading, decide to generate or rewrite ────────────────────
def route_after_grading(state: CRAGState) -> str:
    # If we have enough relevant docs, generate
    if len(state["filtered_docs"]) >= 2:
        return "generate"
    # If we've already retried once, generate anyway (avoid infinite loop)
    if state["retry_count"] >= 1:
        print("[Route] Max retries reached. Generating with available context.")
        return "generate"
    # Otherwise rewrite the query and try again
    return "rewrite_query"

# ─── Build CRAG graph ─────────────────────────────────────────────────────────
crag_builder = StateGraph(CRAGState)
crag_builder.add_node("retrieve",      retrieve_node)
crag_builder.add_node("grade_docs",    grade_documents_node)
crag_builder.add_node("rewrite_query", rewrite_query_node)
crag_builder.add_node("generate",      generate_node)

crag_builder.add_edge(START,           "retrieve")
crag_builder.add_edge("retrieve",      "grade_docs")
crag_builder.add_conditional_edges(
    "grade_docs",
    route_after_grading,
    ["generate", "rewrite_query"],
)
crag_builder.add_edge("rewrite_query", "retrieve")   # loop back with new query
crag_builder.add_edge("generate",      END)

crag_graph = crag_builder.compile()

result = crag_graph.invoke({
    "messages":       [HumanMessage(content="How does Azure AI Search handle semantic ranking?")],
    "question":       "How does Azure AI Search handle semantic ranking?",
    "retrieved_docs": [], "filtered_docs": [],
    "context": "", "answer": "", "retry_count": 0,
})
print(result["answer"])

Pattern 3 — Self-RAG with Hallucination Check

Self-RAG adds a post-generation step that checks whether the answer is grounded in the retrieved documents (no hallucination) and actually answers the question. If either check fails, the graph regenerates.

self_rag.py 
from pydantic import BaseModel, Field
from typing import Literal

# ─── Grading schemas ──────────────────────────────────────────────────────────
class HallucinationGrade(BaseModel):
    score: Literal["yes", "no"] = Field(
        description="'yes' if the answer is fully grounded in the documents, 'no' if it hallucinated."
    )

class AnswerGrade(BaseModel):
    score: Literal["yes", "no"] = Field(
        description="'yes' if the answer actually addresses the question, 'no' if it does not."
    )

hallucination_grader = llm.with_structured_output(HallucinationGrade)
answer_grader        = llm.with_structured_output(AnswerGrade)

# ─── Self-RAG state extends basic RAGState ────────────────────────────────────
class SelfRAGState(CRAGState):
    generation_count: int   # avoid infinite regeneration loop

# ─── Node: Check for hallucinations ──────────────────────────────────────────
def check_hallucination_node(state: SelfRAGState) -> dict:
    prompt = (
        f"Context:\n{state['context']}\n\n"
        f"Answer:\n{state['answer']}\n\n"
        "Is the answer fully supported by the context documents?"
    )
    result = hallucination_grader.invoke([HumanMessage(content=prompt)])
    print(f"[Hallucination Check] Grounded: {result.score}")
    # We don't update state here — we just use the result in the router.
    # Store the grade result as a flag so the router can read it.
    return {"_hallucination_ok": result.score == "yes"}   # custom flag field

# ─── Node: Check if answer is useful ─────────────────────────────────────────
def check_answer_node(state: SelfRAGState) -> dict:
    prompt = (
        f"Question: {state['question']}\n\n"
        f"Answer:\n{state['answer']}\n\n"
        "Does this answer actually address the question?"
    )
    result = answer_grader.invoke([HumanMessage(content=prompt)])
    print(f"[Answer Check] Useful: {result.score}")
    return {"_answer_useful": result.score == "yes"}

# ─── Routers ─────────────────────────────────────────────────────────────────
def route_after_hallucination(state: SelfRAGState) -> str:
    if state.get("_hallucination_ok") and state["generation_count"] < 3:
        return "check_answer"   # grounded → check usefulness
    if state["generation_count"] >= 3:
        return END              # too many retries → stop
    return "generate"           # hallucinated → regenerate

def route_after_answer_check(state: SelfRAGState) -> str:
    if state.get("_answer_useful"):
        return END              # useful answer → done!
    if state["generation_count"] >= 3:
        return END              # too many retries → stop
    return "rewrite_query"      # not useful → rewrite query and retry

2 — Async Graphs for High Throughput

Use ainvoke and astream (async versions) so that one slow LLM call doesn't block your entire server. This requires your node functions to be async def.

async_graph.py 
from langgraph.graph import StateGraph, MessagesState, START, END

# ─── Make nodes async ─────────────────────────────────────────────────────────
async def async_chatbot(state: MessagesState) -> dict:
    # ainvoke → non-blocking LLM call
    response = await llm.ainvoke(state["messages"])
    return {"messages": [response]}

async def async_retrieve(state) -> dict:
    # Run multiple async operations concurrently with asyncio.gather
    import asyncio
    query = state["question"]
    docs, other_data = await asyncio.gather(
        vector_store.asimilarity_search(query, k=4),   # async search
        some_async_api_call(query),                     # any other async call
    )
    return {"retrieved_docs": docs, "extra": other_data}

# Build with async nodes (same API as sync)
builder = StateGraph(MessagesState)
builder.add_node("chatbot", async_chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)
async_graph = builder.compile()

3 — Error Handling and Retries

error_handling.py 
from langgraph.graph import StateGraph, START, END
from langchain_core.messages import AIMessage
import asyncio

# ─── Option 1: Retry policy on a node ────────────────────────────────────────
from langgraph.pregel import RetryPolicy

builder = StateGraph(MessagesState)

builder.add_node(
    "chatbot",
    async_chatbot,
    retry=RetryPolicy(
        max_attempts=3,                     # retry up to 3 times
        retry_on=(Exception,),              # retry on any exception
        backoff_factor=2.0,                 # exponential backoff: 1s, 2s, 4s
        initial_interval=1.0,               # start with 1 second wait
    ),
)

# ─── Option 2: Catch errors in the node itself ────────────────────────────────
async def safe_chatbot(state: MessagesState) -> dict:
    try:
        response = await llm.ainvoke(state["messages"])
        return {"messages": [response]}
    except Exception as e:
        # Return a graceful fallback message instead of crashing
        error_msg = AIMessage(
            content="I'm temporarily unavailable. Please try again in a moment."
        )
        # Log the real error for monitoring
        print(f"LLM error: {type(e).__name__}: {e}")
        return {"messages": [error_msg]}

# ─── Option 3: Fallback node ─────────────────────────────────────────────────
def error_fallback_node(state: MessagesState) -> dict:
    """Catch-all error handler node."""
    return {"messages": [AIMessage(content="An error occurred. Please try again.")]}

# Route to fallback on unexpected errors
def route_with_fallback(state: MessagesState) -> str:
    if state.get("_error"):
        return "fallback"
    return END

main.py — production FastAPI entry point 
import os
from contextlib import asynccontextmanager
from fastapi import FastAPI, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from langchain_core.messages import HumanMessage, AIMessageChunk
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

# Ensure LangSmith tracing is configured before any graph imports
os.environ.setdefault("LANGCHAIN_TRACING_V2", "true")

# ─── Request / Response models ────────────────────────────────────────────────
class ChatRequest(BaseModel):
    thread_id: str
    message:   str
    user_id:   str = "anonymous"

class ChatResponse(BaseModel):
    reply:     str
    thread_id: str

# ─── App lifespan — setup + teardown ─────────────────────────────────────────
graph_instance = None

@asynccontextmanager
async def lifespan(app: FastAPI):
    global graph_instance
    # Setup: connect to PostgreSQL and compile graph
    async with AsyncPostgresSaver.from_conn_string(os.environ["POSTGRES_URI"]) as cp:
        await cp.setup()
        from graph_definition import build_graph   # your graph module
        graph_instance = build_graph().compile(checkpointer=cp)
        yield   # app is running
    # Teardown: connection closes automatically

app = FastAPI(title="LangGraph API", lifespan=lifespan)

# ─── Synchronous chat endpoint ────────────────────────────────────────────────
@app.post("/chat", response_model=ChatResponse)
async def chat(req: ChatRequest):
    if graph_instance is None:
        raise HTTPException(status_code=503, detail="Graph not initialised")

    config = {
        "configurable": {"thread_id": req.thread_id},
        "metadata": {"user_id": req.user_id},
    }
    result = await graph_instance.ainvoke(
        {"messages": [HumanMessage(content=req.message)]},
        config,
    )
    return ChatResponse(
        reply=result["messages"][-1].content,
        thread_id=req.thread_id,
    )

# ─── Streaming chat endpoint ─────────────────────────────────────────────────
@app.post("/chat/stream")
async def chat_stream(req: ChatRequest):
    if graph_instance is None:
        raise HTTPException(status_code=503, detail="Graph not initialised")

    config = {"configurable": {"thread_id": req.thread_id}}

    async def event_generator():
        async for msg_chunk, _ in graph_instance.astream(
            {"messages": [HumanMessage(content=req.message)]},
            config,
            stream_mode="messages",
        ):
            if isinstance(msg_chunk, AIMessageChunk) and msg_chunk.content:
                yield f"data: {msg_chunk.content}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(event_generator(), media_type="text/event-stream")

# ─── Health check ─────────────────────────────────────────────────────────────
@app.get("/health")
async def health():
    return {"status": "ok", "graph_ready": graph_instance is not None}

Production Checklist

✓

Use PostgreSQL checkpointer

Replace MemorySaver/SqliteSaver with AsyncPostgresSaver for multi-instance deployments. Use Azure Database for PostgreSQL.

✓

Use async nodes and ainvoke/astream

Async prevents one user's slow LLM call from blocking all other requests on the same server.

✓

Enable LangSmith tracing

Set LANGCHAIN_TRACING_V2=true. Every graph run is automatically logged — invaluable for debugging production issues.

✓

Add RetryPolicy to LLM nodes

Azure OpenAI has rate limits. A RetryPolicy with exponential backoff handles transient 429/503 errors automatically.

✓

Store secrets in Azure Key Vault

Never hard-code API keys. Use Azure Key Vault + managed identity to inject secrets as environment variables at runtime.

✓

Set max_concurrency on long graphs

For graphs with many parallel branches, set config={"max_concurrency": 5} to cap simultaneous LLM calls and stay within rate limits.
